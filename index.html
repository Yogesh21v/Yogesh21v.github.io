Full-Stack · Multi-Tenant Recruitment Workspace

Talent Finder, Recruiter Portal

Code ↗

A multi-tenant recruiter workspace: build a candidate pool, define job orders, and see candidates ranked by how many required skills they match, then shortlist the best fits in one click.

Skills live in their own table with candidate and job-order junction tables, so ranking is a plain SQL join on the count of distinct matching skills instead of string parsing. Every list and detail endpoint takes a tenant id and checks the record really belongs to that tenant. Shortlisting creates a Submission that moves through Shortlisted, Submitted, Interviewing and Offered / Rejected / Hired.

Node.jsExpressMySQL 8mysql2zodmulterVanilla JSPlaywright
Deep dive: how it actually works
  • Layered backend (routes, controllers, services, repositories) with all SQL in the repository layer and zod schemas validating every create and update endpoint.
  • A unique constraint plus a 409 response stops a candidate being shortlisted twice for the same job order.
  • Optional CV upload: a PDF or DOCX is parsed in memory (pdf-parse / mammoth) and scanned for name, email, phone, location, years of experience and known skills. The matches pre-fill an editable form, and unreadable files fall back to the manual form.
  • Hand-curated seed data: three demo tenants (LinkedIn, Naukri, Monster), each with 8 candidates and 4 job orders whose skills overlap on purpose, so ranked matches show on first run.
  • Frontend is plain HTML, CSS and vanilla JavaScript with no build step; the same Express server serves the API and the pages.

Soccer Concierge Chatbot

Code ↗

A chat interface for soccer scores, fixtures, and standings — Lex handles the conversation, three Lambdas handle the work.

The interesting engineering problem here is latency: a chatbot has to feel instant, but looking up real sports data doesn't happen instantly. So the fulfillment Lambda replies with an immediate acknowledgement and hands the real lookup off to an SQS queue; a separate worker Lambda does the actual data-fetching and flips the DynamoDB record to DONE, while the frontend polls for the result.

AWS LambdaAPI GatewayAmazon Lex V2DynamoDBSQSSNS
Deep dive: how it actually works
  • LF0 (API Gateway-facing) forwards chat messages to the Lex bot and exposes a polling endpoint for results.
  • LF1 (Lex fulfillment) handles GreetingIntent / ThankYouIntent / SoccerNewsIntent, writing a PENDING record and enqueuing the real request onto SQS.
  • LF2 (SQS-triggered worker) does the actual soccer-data lookup and marks the DynamoDB record DONE — decoupling 'feels instant' from 'is actually correct'.

AWS Serverless · Face-Recognition Access Control

SmartDoor

Code ↗

Enroll authorized faces, then have a doorbell capture checked against them: GRANTED / DENIED / NO_FACE_DETECTED, logged and alerted.

Enrollment and recognition both use Rekognition against a shared face collection — IndexFaces to register a person, SearchFacesByImage to check a new capture. A similarity threshold decides access, every attempt gets written to an access log, and anything that isn't a clean GRANTED fires an SNS alert. The 'camera' is genuinely real: a small OpenCV script grabs a live frame from a laptop webcam so the whole enroll → capture → decide loop can be run end-to-end, not just simulated from static files.

AWS RekognitionLambdaDynamoDBSNSOpenCV
Deep dive: how it actually works
  • Client-chosen identifiers embedded in the S3 key (enroll/<name>/..., captures/<capture-id>/...) let the uploading client poll for its own result immediately, without waiting on a server-assigned ID.
  • A custom NoFaceDetectedError wraps Rekognition's InvalidParameterException, keeping the access-decision logic decoupled from botocore-specific exception types.
  • Rekognition has no native CloudFormation resource type for a face collection, so collection setup/teardown is a deliberate one-time manual script rather than something baked into the SAM template.

Information Retrieval · Bayesian Language Model

News Article Retrieval Engine

Code ↗

A search engine over 210k+ HuffPost headlines that ranks by probability, not just keyword overlap.

Instead of scoring documents by raw term frequency, this implements a hierarchical smoothed language model — a document's term probabilities are backed off through its category and the whole collection (Ponte & Croft's language-modeling approach to IR, with Zhai & Lafferty-style smoothing). That backoff is what lets a document score reasonably for a query term it never literally contains, if its category commonly uses that term — a genuine Bayesian-inference advantage over plain keyword matching.

PythonBayesian InferenceNLPInformation Retrieval
Deep dive: how it actually works
  • P_smoothed(term|doc) = λ_doc·P(term|doc) + λ_category·P(term|category) + λ_collection·P(term|collection), with documents ranked by summed log query-likelihood.
  • bayesian_model.py also implements P(category|query) via Bayes' rule with a naive conditional-independence assumption, to infer a query's most likely category.
  • Evaluated with precision@k, recall@k, and Mean Average Precision (MAP) against category-labeled relevance judgments.
✓ 56 tests · full pipeline exercised end-to-end on a synthetic sample dataset
Deep Learning · LipNet Architecture

Lip Reading AI

Code ↗

Predicts spoken text from silent video of a speaker's mouth — no audio, just frames.

Video frames get grayscaled, cropped to the mouth region, and fed through 3D convolutions (to capture motion across frames, not just spatial features) into bidirectional LSTMs, trained with CTC loss so the model doesn't need frame-perfect alignment between video and transcript. One real gotcha: Keras's CTC loss always treats the last vocabulary index as the blank token, which silently breaks training if your vocabulary was designed with blank at index 0 — worth knowing before you spend an afternoon debugging a model that refuses to converge.

TensorFlowKerasOpenCV3D CNNBi-LSTMCTC Loss
Deep dive: how it actually works
  • 3× [Conv3D → ReLU → MaxPool3D] for spatio-temporal feature extraction, then 2× Bidirectional LSTM(128) with dropout for sequence modeling, then a per-timestep character softmax.
  • Ships a small Streamlit demo ("LipBuddy") that shows the original clip next to the exact preprocessed frames the model sees, plus the ground-truth alignment and prediction.
  • Tests run entirely on synthetically generated clips — no multi-GB GRID dataset download required to prove the pipeline and model are wired correctly, including a real forward+CTC-loss+backward training step.
